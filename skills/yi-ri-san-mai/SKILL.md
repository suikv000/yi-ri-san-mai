# 一日三麦

先守预算，再看能量和蛋白质；给出具体食物、数量、门店、购买方式和待调整差距。

## 读取需求

使用已知的周预算及口径、身高、体重、年龄、公式性别参数、活动量、减脂/维持/增肌目标、力量训练、饮食禁忌及过敏信息。只问影响结果的缺项，不把演示档案当成用户资料。

比价需要用户允许的城市及家、公司或商圈位置。只有一个地点时只围绕该中心查店；没提供公司与上下班安排，不能声称算出了通勤最优路线。无需精确住址即可先查商圈。将计划覆盖的餐次、可接受距离、用餐时段和保留餐次纳入约束。

涉及营养估算与费用计算时读 [计算与输出规则](references/planning.md)。需要当前价格或供应时读 [MCP 调用流程](references/mcd-mcp.md)，实际查询后再给实时结论。

## 查询与比较

- 发现工具及参数定义，按实际 schema 查询附近门店、各店菜单、套餐轮次/选项、精确营养和价格。以同店、同数量、同规格、同取餐渠道和兼容时段比较。
- 同时考虑单点、1+1、官方套餐、套餐加购；不为凑套餐强行添加薯条或饮品。选项不可用、无完整报价或营养匹配未知时说明缺项，不套别店价格、不当作0元、不猜新品营养。
- 内部价格组编号未返回时，直接逐店核价；不能将单品价差当整店折扣系数。菜单起价不代表任意套餐组成价格。
- 已知同一食物集合可用 `scripts/plan.cjs` 所用的精确覆盖思路比较购买路径。整周启发式方案不宣称全局最优。复合加购单元合计与整单最终核价分别标明。
- 卡券必须核对用户权益、有效期、使用次数、门店时段和互斥。未知兼容性不叠加优惠。分开列新卡现金支出、周分摊与每次享惠成本；未使用卡仍保留费用，储值余额不是折扣。
- 按实际食物数量累计热量、蛋白质、碳水、脂肪、钠；缺失纤维、饱和脂肪、过敏原保持未知。优先补全天合理缺口，蛋白质/元和蛋白质/100千卡用于解释，不无上限堆蛋白质。

## 生成与调整

给出7天表：每餐组成、份数、门店、单点/套餐购买路径、价格、营养；每日合计和参考差距；整周现金及含卡费折算；价格时间、范围与待核实项。预算无解时保留上限并说明可行取舍，不少算餐次或隐藏费用。

单餐替换只改该餐，重算整周预算与当天营养，其余20餐保持。锁定是单独选择；整周重排保留锁定。用户改预算或档案时先确认正在采用的条件，不把旧结果标为新条件结果。

默认提供简洁摘要，详细购买路径及数据依据按需展开。可用同心三层环表达热量、蛋白质和脂肪比例，同时保留实际值/目标值，超过目标明确显示；满环不是营养全面的判定。

## 快照与能力边界

随包 [公开快照](references/snapshot.json) 是2026-10-18读取记录，地点为天津时代奥城，早餐预约10月19日08:15，不能冒充今日或下一周价格。离线演算可执行：

```sh
node scripts/plan.cjs --budget 450 --goal loss
```

脚本默认使用明确标为示例的175cm/75kg/30岁档案；给用户实际配餐时先换成其参数。用户可用 `--settings profile.json` 提供参数；输入只读取，不自动保存。脚本输出标识 snapshot，并保留营养缺口。

如果用户请求每周日提醒、手机助手或到点下单，解释其宿主依赖。只有宿主工具已连接、用户明确授权且当前支持时才配置；未配置不能说已创建。未来菜单通常无法核实整周，先出估算、临餐复核。此包不执行账户、领券、购卡、订单、付款或外部消息工具；交易交给支持该功能的独立流程与用户确认。普通报名/安装不等于用户授权消费。
